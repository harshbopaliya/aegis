What this service is

Enterprises want AI agents that can operate APIs and databases — but giving an LLM direct production access is fragile. The Safety Gateway sits in the path: agents submit structured proposals (verb, resource id, environment label, minimal payload). Your organization decides what executes, after automated enforcement and optional human sign-off.

Guardrails, not blind trust

RBAC-style token scope, configurable policies (block / allow / require approval), simulated impact, and numeric risk scoring.

One choke point

Execution flows through adapters you deploy in your environment. Agents never bypass the gateway to reach production.

Observable & accountable

Operators see pipelines, approvals, and audit events — metadata about decisions, not your proprietary row-level data.

How it works (high level)

Trigger can be a user, scheduler, or autonomous agent — all paths converge on the same evaluation pipeline before execution.

User / System / Agent
→ Safety Gateway
  → Token scoping → Policy → Sandbox → Risk score → Human approval (if needed)
→ Execution adapter (inside your boundary) → APIs / DB / external systems
→ Observability & audit (events) · Backup / recovery hooks

Privacy: production data stays secret

For your first deployment model, assume the gateway never sees raw production rows. Execution happens where you run the adapter — with credentials that never leave your trust zone.

Safety Gateway (this service)

  • Receives action proposals: HTTP verb, logical resource id (e.g. table:orders), environment label, actor id.
  • Stores policy outcomes, risk scores, simulation summaries, approval decisions.
  • Dashboard shows pipelines and audit events — operational telemetry.
↔

Your production zone (private)

  • Secrets stay here: DB connection strings, API keys, PII, payment data, internal payloads.
  • The execution adapter applies approved actions using credentials only available inside your VPC / tenant.
  • You can configure payloads so the gateway receives hashes or opaque ids instead of sensitive bodies.
What we deliberately do not require for guardrails: bulk exports of production tables, full prompt logs attached to payloads, or dashboard access to your live datastore. Audit entries describe what was evaluated, not your customer records.
Item Gateway / dashboard typically sees Stays secret on client side
Production rows & column values No Yes — unless you explicitly choose to send them (not recommended).
API keys / DB passwords No Yes — remain in your adapter runtime.
Action verb, resource key, env label Yes You control identifiers; avoid embedding secrets.
Policy blocks, risk tier, approvals Yes Governance visibility without raw data.

How any client uses this service

A typical onboarding looks like this. Exact networking depends on whether we host SaaS or you deploy on-premises — the trust boundary stays the same.

Provision gateway endpoint

You receive a dedicated HTTPS URL (or deploy the gateway inside your VPC). TLS terminates at your edge or ours.

Issue credentials

API credentials or mutual TLS clients are issued only to your AI runtime and ops tools. Production datastore credentials stay with your execution adapter.

Point agents at POST /v1/actions

Agents send structured proposals instead of calling production APIs directly. Low-privilege tokens limit verbs per role.

Deploy execution adapter next to production

The adapter listens for approved intents or invokes synchronously after gateway clearance — applying changes with your secrets.

Human operators use approvals & dashboard

High-risk flows pause at POST /v1/approvals. Operators monitor pipelines without needing database replicas on our side.

Production minimize payloads: in production integrations, configure adapters so audit payloads exclude PII — send references or hashes only.
